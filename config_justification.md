# Configuration Justification (`config_justification.md`)

This document justifies every non-default configuration setting across `docker-compose.yml`, `Dockerfile.mrjob`, `config/hdfs-configs/core-site.xml`, `config/hdfs-configs/hdfs-site.xml`, `config/yarn-configs/yarn-site.xml`, `config/yarn-configs/mapred-site.xml`, and `userfiles/mapreduce/mrjob.conf`.

## 1. Docker Compose & Container Image (`docker-compose.yml` & `Dockerfile.mrjob`)

| Service / Scope | Setting | Justification (What it does · Why chosen · Impact of removal/change) |
| :--- | :--- | :--- |
| `namenode`, `datanode1`–`3`, `resourcemanager` | `image: apache/hadoop:3.5.0` | Pins the official Apache Hadoop 3.5.0 runtime image across all core storage and resource management daemons. Version 3.5.0 was chosen to guarantee binary, RPC protocol, and Hadoop Streaming JAR (`hadoop-streaming-3.5.0.jar`) compatibility across the cluster. Using unpinned (`latest`) or mismatched tags could introduce RPC version mismatches between the NameNode, DataNodes, and YARN ResourceManager. |
| `nodemanager`, `client` (`Dockerfile.mrjob`) | `image: ca1-hadoop-mrjob:3.5.0` (`/opt/mrjob-venv` with `mrjob==0.7.4`, `PyYAML==6.0.2`, `setuptools==75.8.0`) | Extends `apache/hadoop:3.5.0` with an isolated Python 3.12 virtual environment containing `mrjob`, `PyYAML`, and `setuptools` (`distutils`). This was chosen because Ubuntu 24's base Python 3.12 omits `pip` and `distutils`, which `mrjob 0.7.4` requires on both the submitting client and the executing YARN NodeManager containers. Removing this custom image causes `mrjob` job submissions to fail with `No module named 'mrjob'` on the client or `PipeMapRed.waitOutputThreads(): subprocess failed with code 1` (`No module named 'distutils'`) inside YARN map tasks. |
| `datanode1`, `datanode2`, `datanode3` | Three distinct DataNode services (`hostname: datanode1..3`) | Launches three independent HDFS DataNode containers on the Docker bridge network. Three DataNodes were chosen to satisfy the Progress Update 1 fault-tolerance requirement with `dfs.replication=2`, ensuring at least one additional live DataNode is available to receive re-replicated blocks when a DataNode is stopped. Running only two DataNodes with replication factor 2 would leave no third target node for automatic re-replication during a node failure. |
| `namenode` | `./namenode_data:/opt/hadoop/data/name` | Bind-mounts the host `./namenode_data` directory to the NameNode metadata directory inside the container. This was chosen so the HDFS namespace (`fsimage` and `edits` logs) persists across container restarts on the host filesystem. Removing this mount would store metadata inside ephemeral container storage, wiping the entire HDFS directory tree whenever the NameNode container is recreated. |
| `datanode1`–`3` | `./datanodeX_data:/opt/hadoop/data/data` | Bind-mounts a dedicated host directory (`datanode1_data`, `datanode2_data`, `datanode3_data`) into each DataNode's block storage path. Separate host directories were chosen so each DataNode maintains an isolated block pool and storage UUID (`DS-...`) that survives container restarts. Sharing a single host folder across DataNodes or omitting the mounts would cause storage-ID lock conflicts or permanent block loss on container recreation. |
| All services | `./config/.../*.xml:/opt/hadoop/etc/hadoop/*.xml:ro` | Mounts the host Hadoop XML and `log4j.properties` configuration files read-only (`:ro`) into `/opt/hadoop/etc/hadoop/`. Read-only bind mounts were chosen so all seven containers share identical, version-controlled configurations without rebuilding images on config edits. Removing `:ro` or omitting these mounts would cause daemons to revert to stock defaults (such as local `file:///` filesystem and standalone runner). |
| `client` (`hadoop-client`) | `./:/workspace` and `working_dir: /workspace` | Mounts the entire `CA1_BDATA` project workspace into `/workspace` inside `hadoop-client` and sets it as the default working directory. This allows seamless access to local datasets (`userfiles/CA1_Datasets/`), cleaned outputs (`userfiles/processed_data/`), and MapReduce scripts (`userfiles/mapreduce/`) when running `hdfs dfs -put` and `mrjob` commands. Removing this mount would require manually copying gigabytes of CSVs into the container with `docker cp`. |
| `namenode`, `resourcemanager`, `nodemanager` | Ports `9870:9870`, `9000:9000`, `8088:8088`, `8042:8042` | Publishes the NameNode Web UI (`9870`), NameNode IPC endpoint (`9000`), YARN ResourceManager Web UI (`8088`), and NodeManager Web UI (`8042`) to the Windows host. These port mappings were chosen to inspect HDFS block distribution, browse `/sg_mobility/`, and capture YARN application and container evidence from the host browser. Removing them would make the web UIs unreachable from `localhost`. |
| All services | `user: root` and `HDFS_NAMENODE_USER=root` / `HDFS_DATANODE_USER=root` | Runs the Hadoop daemons as `root` inside the isolated Docker containers and authorizes `root` to start HDFS services. This was chosen to avoid UID/GID permission errors when writing to Windows-mounted host volumes (`namenode_data`, `datanodeX_data`, `/workspace`). Removing these settings causes permission-denied errors on bind-mounted directories or daemon startup refusal in Hadoop 3.x. |
| `namenode` | Conditional `hdfs namenode -format -nonInteractive` in `command` | Checks whether `/opt/hadoop/data/name/current` exists before formatting the NameNode and launching `hdfs namenode`. This was chosen so the cluster formats automatically on its very first boot while preserving existing HDFS metadata on subsequent restarts. Unconditionally formatting on every start would generate a new `clusterID`, rendering all existing DataNode block pools incompatible. |
| `client` (`hadoop-client`) | `tty: true`, `stdin_open: true`, `command: sleep infinity` | Keeps the `hadoop-client` container running indefinitely with an attached pseudo-TTY. This was chosen so `hadoop-client` acts as a persistent interactive workstation for `docker compose exec` job submissions and HDFS administration. Without `sleep infinity`, the client container would exit immediately after startup. |
| All services | `restart: unless-stopped` | Instructs Docker to automatically restart any container that exits unexpectedly unless explicitly stopped by the user (`docker stop`). This was chosen to recover automatically from transient startup race conditions while still allowing controlled DataNode stops (`docker stop datanode2`) during the HDFS fault-tolerance test. Setting `restart: always` could interfere with manual stop tests across Docker daemon restarts, while `no` would leave services down after a transient error. |

## 2. Core Hadoop Configuration (`config/hdfs-configs/core-site.xml`)

| Property | Value | Justification (What it does · Why chosen · Impact of removal/change) |
| :--- | :--- | :--- |
| `fs.defaultFS` | `hdfs://namenode:9000` | Sets the default distributed filesystem URI and NameNode RPC address for all HDFS clients and YARN containers. `namenode:9000` was chosen to match the Docker service hostname `namenode` and port `9000`. Removing it causes Hadoop commands (`hdfs dfs -ls`) and MapReduce jobs to default to the container's local filesystem (`file:///`) instead of HDFS. |
| `hadoop.tmp.dir` | `/opt/hadoop/data` | Defines the base directory for temporary Hadoop runtime files and storage subdirectories. `/opt/hadoop/data` was chosen to place temporary state inside a dedicated path under `/opt/hadoop` rather than `/tmp`. Leaving it at the default `/tmp/hadoop-${user.name}` risks data loss when OS temporary directories are cleaned. |
| `hadoop.http.staticuser.user` | `root` | Specifies the username assumed for unauthenticated HTTP web UI requests on ports `9870` and `8088`. `root` was chosen so the browser file browser (`Utilities -> Browse the file system`) and `fsck` endpoints can inspect `/sg_mobility/` files owned by `root` without Kerberos authentication. Removing it defaults the web user to `dr.who`, which restricts file inspection and directory actions in the Web UI. |

## 3. HDFS Configuration (`config/hdfs-configs/hdfs-site.xml`)

| Property | Value | Justification (What it does · Why chosen · Impact of removal/change) |
| :--- | :--- | :--- |
| `dfs.replication` | `2` | Sets the default block replication factor for files written to HDFS. A value of `2` was chosen as required by the CA1 specification (Task 1) to guarantee fault tolerance across the 3-DataNode cluster while consuming 33% less disk space than the default replication factor of `3`. Changing it to `1` would eliminate fault tolerance (stopping one DataNode would make blocks unreadable), while `3` would place every block on all three DataNodes, preventing re-replication observation when one node stops. |
| `dfs.namenode.name.dir` | `file:///opt/hadoop/data/name` | Specifies the local directory inside the `namenode` container where the namespace image (`fsimage`) and edit logs are stored. This path was chosen to match the host bind mount `./namenode_data:/opt/hadoop/data/name` in `docker-compose.yml`. Changing it to a path outside the mounted volume caused container crash loops and metadata loss before our path fix. |
| `dfs.datanode.data.dir` | `file:///opt/hadoop/data/data` | Specifies the local directory inside each `datanode` container where HDFS data blocks are stored. This path was chosen to match the `./datanodeX_data:/opt/hadoop/data/data` volume mounts in `docker-compose.yml`. Removing or changing it breaks the mapping to persistent host storage. |
| `dfs.blocksize` | `4194304` (4 MB) | Sets the HDFS block size to 4 MB (4,194,304 bytes) instead of the Hadoop default of 128 MB. A 4 MB block size was chosen so our datasets (`rainfall_clean.csv` at 50.6 MB -> 13 blocks, `carpark_clean.csv` at 100.6 MB -> 26 blocks, and `bus_od_clean.csv` at 717.6 MB -> 180 blocks) split into multiple blocks distributed visibly across all three DataNodes and spawn parallel Map tasks on YARN. With the default 128 MB block size, `rainfall_clean.csv` and `carpark_clean.csv` would each occupy only 1 block, limiting block-distribution analysis and mapper parallelism. |
| `dfs.heartbeat.interval` | `2` | Sets the interval in seconds between DataNode-to-NameNode heartbeats (default is `3` seconds). A 2-second interval was chosen to speed up cluster liveness reporting during our controlled DataNode failure and recovery demonstration. Increasing it would delay detection of stopped or rejoined DataNodes. |
| `dfs.namenode.heartbeat.recheck-interval` | `10000` (10 seconds) | Sets the interval in milliseconds (`10,000 ms` = 10s, down from the default `300,000 ms` = 5 minutes) at which the NameNode checks for expired DataNodes (`2 * recheck-interval + 10 * heartbeat.interval` = **40 seconds** total dead-node timeout instead of 10.5 minutes). This value was chosen so that stopping a DataNode during the Progress Update 1 fault-tolerance test triggers dead-node marking and automatic block re-replication onto the third DataNode within ~40 seconds rather than waiting over 10 minutes. Removing this setting would force a 10m 30s wait before HDFS begins re-replicating under-replicated blocks. |

## 4. YARN & MapReduce Configuration (`yarn-site.xml`, `mapred-site.xml`, and `mrjob.conf`)

| Property | Value | Justification (What it does · Why chosen · Impact of removal/change) |
| :--- | :--- | :--- |
| `mapreduce.framework.name` (`mapred-site.xml` & `mrjob.conf`) | `yarn` | Directs Hadoop MapReduce to execute jobs on the distributed YARN cluster rather than the local in-process runner (`local`). This was chosen to satisfy Task 1 and Task 2 requirements that all `mrjob` analyses execute on YARN containers. Removing it causes jobs to run locally inside the client process with zero YARN applications recorded in ResourceManager. |
| `yarn.resourcemanager.hostname` (`yarn-site.xml` & `mrjob.conf`) | `resourcemanager` | Tells the NodeManager and submitting clients the hostname of the YARN ResourceManager container. `resourcemanager` was chosen to match the Docker service name on the bridge network. Removing it defaults the address to `0.0.0.0`, preventing `hadoop-client` and `nodemanager` from connecting to the ResourceManager. |
| `yarn.nodemanager.aux-services` & `...mapreduce.shuffle.class` | `mapreduce_shuffle` / `org.apache.hadoop.mapred.ShuffleHandler` | Enables the auxiliary Shuffle HTTP service on the YARN NodeManager so Reduce tasks can fetch partitioned intermediate outputs from Map tasks. This is mandatory for any MapReduce job on YARN. Removing it causes all MapReduce jobs to fail at the transition from Map to Reduce (`Invalid AuxService`). |
| `yarn.acl.enable` | `false` | Disables YARN access control lists inside the single-tenant Docker teaching cluster. This was chosen so `root` and web UI users can view application logs and statuses without ACL permission denials. Enabling ACLs without configuring user groups could block log inspection. |
| `yarn.nodemanager.env-whitelist` | `JAVA_HOME,HADOOP_COMMON_HOME,...` | Whitelists essential Hadoop and Java environment variables so the NodeManager passes them into spawned Map and Reduce containers. This was chosen so Hadoop Streaming and Python subprocesses inside YARN containers can locate Java and Hadoop libraries. Removing it causes container launch failures due to missing `JAVA_HOME` or `HADOOP_HOME`. |
| `yarn.log-aggregation-enable`, `remote-app-log-dir`, `retain-seconds` | `true`, `/tmp/logs`, `604800` (7 days) | Aggregates container `stdout`, `stderr`, and `syslog` files from the NodeManager into HDFS (`/tmp/logs`) upon job completion and retains them for 7 days. This was chosen so we could run `yarn logs -applicationId <id>` from `hadoop-client` to diagnose the Python 3.12 `distutils` traceback. Disabling log aggregation makes completed container logs inaccessible via `yarn logs`. |
| `hadoop_streaming_jar` (`mrjob.conf`) | `/opt/hadoop/share/hadoop/tools/lib/hadoop-streaming-3.5.0.jar` | Explicitly provides the path to the Hadoop 3.5.0 Streaming JAR inside the container for `mrjob`. This was chosen so `mrjob` immediately locates the streaming bridge without searching non-standard paths. Omitting it can cause `mrjob` to fail when locating the streaming JAR. |
| `python_bin` (`mrjob.conf`) | `/opt/mrjob-venv/bin/python3` | Instructs YARN Hadoop Streaming tasks to invoke the virtual environment's Python 3 binary where `mrjob`, `PyYAML`, and `setuptools` (`distutils`) are installed. This was chosen to prevent YARN tasks from invoking system `/usr/bin/python3`, which lacks `distutils` in Ubuntu 24. Changing it back to `python` or `/usr/bin/python3` causes mapper subprocesses to crash with exit code 1. |
| `mapreduce.job.reduces` (`mrjob.conf`) | `2` | Sets the default number of Reduce tasks per MapReduce step to `2`. Two reducers were chosen to demonstrate parallel reduce partitioning across keys (such as `(year_month, day_type)` and `(station_id, date)`) while avoiding excessive container scheduling overhead on a single 8-vCore NodeManager. Setting it to `0` would skip the Reduce phase entirely, violating Task 2's Map+Reduce requirement. |
